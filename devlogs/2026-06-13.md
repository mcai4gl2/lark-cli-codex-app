## Slack Socket Mode Reconnect After Read Timeout

### Problem / Goal
- Investigate why the homelab Codex Slack gateway stopped processing a thread message.
- Keep the local Socket Mode gateway alive across transient Slack WebSocket read failures.
- Use Docker-based Go formatting, testing, and build commands per repository instructions.

### Problems Encountered
- The deployed gateway process was no longer running; `gateway.log` showed `read Slack Socket Mode envelope: read tcp ... read: connection timed out`, followed by exit status 1 at `2026-06-13T16:44:14+08:00`.
- The latest structured Slack event log still only contained the older successful event, so the new thread message was not processed by a live gateway.
- Root cause: `internal/slack/gateway.go` returned any Socket Mode `ReadMessage` error from `Serve`, which made transient WebSocket failures fatal.

### Key Design Decisions
- Added reconnect behavior inside the Slack gateway service rather than relying only on the wrapper script, because the script does not supervise or restart after process exit.
- Reopened Socket Mode with `apps.connections.open` after a socket read/ack failure, using a short fixed delay to avoid a tight reconnect loop.
- Closed the active WebSocket when the service context is canceled so shutdown does not wait indefinitely on a blocking read.

### Solution / Implementation
- Added a regression test with a fake Slack Web API and local WebSocket server that drops the first Socket Mode connection and verifies the gateway reconnects and handles an event from the second connection.
- Split the socket connection handling into a reconnectable `serveSocketConnection` helper.
- Rebuilt and installed the updated CLI to `/home/ligeng/.local/bin/lark`.
- Restarted the homelab gateway with `/home/ligeng/bin/codex-chat-gateway.sh`.

### Results
- Verified the new regression test failed before the fix with `Serve() returned before reconnecting`.
- Verified `docker run --rm -v "$PWD:/work" -w /work golang:1.24 go test ./internal/slack -run TestServiceReconnectsAfterSocketReadError -count=1` passes.

## Slack Gateway Reconnect Observability

### Problem / Goal
- Clarify whether a Socket Mode reconnect log line means the homelab gateway is stuck or recovered.
- Reduce noisy reconnect behavior during repeated connection failures.

### Problems Encountered
- The gateway log showed `reconnecting` after a transient Slack WebSocket close, but the code did not log the subsequent successful connection.
- Without a success log, a recovered gateway looked unstable even while the process was alive and had an established Slack socket.

### Key Design Decisions
- Log `connected to Slack Socket Mode` immediately after a successful WebSocket dial.
- Include the reconnect delay in failure logs.
- Use bounded exponential backoff for repeated open/dial failures while resetting to the initial delay after a successful socket connection.

### Solution / Implementation
- Updated the Slack gateway reconnect loop and socket helper return value to track whether a connection had been established before failure.
- Rebuilt, installed, and restarted the homelab gateway so live logs include the new connection-success line.
