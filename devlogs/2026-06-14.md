## Slack Recover Mode and Processing Reaction

### Problem / Goal
- Avoid requiring users to repost Slack thread messages after the Socket Mode gateway reconnects or restarts.
- Persist known participating Slack threads and last processed timestamps so the gateway can catch up missed replies.
- Add a visible processing reaction while Codex is working on a Slack message, then remove it when processing finishes.

### Problems Encountered
- A final review found that the first catch-up implementation advanced recovery state before message processing succeeded, which could skip messages permanently after event-log, memory, or desktop enqueue failures.
- A second review found another early state advancement path inside `processEntry` before desktop enqueue could fail.
- Both issues were fixed with regression tests so `LastProcessedTS` advances only after successful processing for normalized user messages.

### Key Design Decisions
- Default recover mode is `thread`, which catches up messages in known participating threads without scanning whole channels.
- `mention-dm` and `off` modes are configurable via CLI/config/env.
- Recovery state lives under `.slack/conversations/.state/recover-state.json`.
- The processing reaction defaults to `eyes` and can be disabled with an empty `processing_reaction` or `--processing-reaction ""`.
- Catch-up intentionally marks normalized-out bot/subtype/blank messages processed to avoid repeated scanning.

### Solution / Implementation
- Added Slack recovery state persistence and catch-up normalization for messages returned by `conversations.replies`.
- Added gateway catch-up on startup and after successful Socket Mode reconnects.
- Added agent processing lifecycle hooks and Slack reaction observer for add/remove around Codex processing.
- Added CLI flags and config/env support for recover mode and processing reaction.
- Updated user/deployment docs and saved the implementation plan in `plans/20260613_recover-mode.md`.
